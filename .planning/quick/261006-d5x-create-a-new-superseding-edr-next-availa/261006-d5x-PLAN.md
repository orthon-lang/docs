Decision section: 8 numbered points, each resolving one thesis — do not weaken, merge, or drop any:
  1. Reject the `emit`+`return` dual-channel form: a single function must not use `emit` to produce
     a stream AND a differently-typed `return` to produce a final value multiplexed through the
     same return path. This is the core reversal of EDR-052's Decision section.
  2. Reject the `.final()` accessor — removed from the specification entirely; no iterator exposes
     a `.final()` method.
  3. Accept the replacement model: split across two functions — an outer plain `fun` owning the
     terminal result via ordinary `return`, and a nested `fun` (closing over the outer function's
     `mut` locals) owning the `emit` stream, returning `Iterator<T>`. Reproduce, verbatim and
     character-for-character (including its fence lines), the exact Orthon code example currently
     under `what/concepts/EMIT_AS_INTERMEDIATE_RESULT.md`'s "### Nested `emit` Function —
     Splitting Stream from Terminal Result" heading (the `type Progress(...)` / `fun
     show_progress` / `fun process_data` with nested `fun track_batch` / closing
     `process_data([[10, 20], [30], [40, 5, 60]])` example) — read it from that file, do not
     re-derive or paraphrase the code. Follow it with the same three explanatory paragraphs that
     already accompany it there (multi-variable closure-capture rationale; emit-only-for-variable-
     count rationale; two-channels-two-functions-not-one-`.final()` rationale), copied or closely
     paraphrased.
  4. No new function-declaration keyword for emit-producing functions. Cite, briefly, without
     re-deriving: (a) `gen(...)` is reserved for generator-expression comprehension (EDR-092/093,
     LOCKED); (b) `GENERATORS.md` Principle 1, "`emit` is the sole production keyword — there is no
     second keyword"; (c) `fun`/`proc`/`new` is a closed Mutation-Policy-relative-to-`self` triad
     (`what/SEMANTIC_MODEL.md` § Mutation), orthogonal to the stream-vs-single-value axis.
  5. No new `execution_context` constructor/type for emit-producing functions. Sequential `emit`
     generators need no execution context at all — fully specified by EDR-021/EDR-050 (lazy
     pull-based, state machine, suspend/resume at `next()`). If intermediate results ever
     genuinely originate from parallel work, EDR-085's existing `spawn()`/`fork()` constructors
     (decision point 6: submissions "join the generator stream," `next()`/`stop()`, `grab`/
     `gather`) already cover it — no new primitive either way.
  6. Emit-applicability criterion: use `emit` only when a single invocation can genuinely produce a
     variable count of items (0, 1, or many — not statically fixed at exactly one on every path).
     If every path through a function body contains exactly one `emit`, that is a signal to use
     plain `return` instead.
  7. Elevate point 6 into a compiler-diagnostic recommendation: static reachability analysis over a
     function's CFG can determine whether every path contains exactly one `emit` (no path has zero
     or multiple); when so, the compiler SHOULD suggest rewriting to plain `return`. Frame this
     using `COMPILER_AS_STATIC_ANALYZER.md`'s own vocabulary — reference its layered-verification
     model (this is a Layer 6 Exhaustiveness & Completeness-class check) and its diagnostic shape
     (machine-readable `code`/`severity`/`location`/`repair_hint`) rather than inventing new terms.
  8. Retract EDR-052's Principle 2 ("Intermediate ≠ lazy… the computation drives itself") as a
     DIRECT CONSEQUENCE of point 1 — state this as a consequence, not an independently-justified
     decision. All `emit` in the language is PULL-based (consumer-driven, lazy) per
     EDR-021/EDR-050/EDR-091 (cite `what/concepts/LAZY_SEQUENCE_GENERATORS.md`'s desugaring
     description near "`emit` keyword desugars to storing the current value and control flow
     state..."); no push-based `emit` mode exists anywhere in the language.

Consequences section — honest Positive/Negative, not boilerplate:
  Positive: removes the `let x = f()`/`Iterator<T>` ambiguity and the hidden-second-channel
  problem; two result channels -> two functions -> two owners is simpler than one function
  multiplexing two channels through one return path plus an accessor; removes `.final()` and its
  per-iterator final-value storage slot from every `emit`-using function's required state-machine
  surface; keeps `emit` strictly within its existing pull-based contract — no second execution
  discipline, no contradiction between a "computation drives itself" principle and the
  actually-specified consumer-driven protocol; gives programmers, LLM code generators, and (per
  point 7) the compiler itself a crisp, mechanically checkable rule for choosing `emit` vs `return`;
  zero new syntax, zero new keyword, zero new `execution_context` constructor.
  Negative: computations whose variable-count stream and one-shot final result are tightly coupled
  now need two function declarations (one nested) where EDR-052 allowed one — a minor ergonomics
  cost, mitigated by closure capture doing the data-sharing job `.final()`'s stored iterator state
  used to do; the compiler-diagnostic recommendation (point 7) is a SHOULD-level recommendation, not
  yet a fully specified compiler pass — its concrete activation/severity is deferred to future
  Phase 7 / implementation-repo work, this EDR commits to the criterion, not to shipping code; other
  project prose referencing `.final()`/dual-channel beyond the three files this task's Task 2/3
  touch may still exist and need a future sweep — this EDR's Compliance only guarantees those
  specific files.

Compliance section — verifiable rules:
  1. No accepted (`what/`) document recommends a function using `emit` together with a
     differently-typed `return` retrieved via `.final()`; where such content remains for historical
     reference, it is explicitly marked WITHDRAWN.
  2. `.final()` does not appear as an active `Iterator<T>` method in any accepted specification
     text — only in withdrawal/historical notes.
  3. A computation needing both a variable-count stream and a one-shot terminal result is specified
     as two functions: an outer plain `fun` returning the terminal result via `return`, and a
     nested `fun` (closing over the outer function's `mut` locals as needed) returning
     `Iterator<T>` via `emit`.
  4. `fun`/`proc`/`new` remains a closed, three-member declaration triad.
  5. `execution_context`'s constructor set (`defer`/`delegate`/`spawn`/`fork`) remains closed per
     EDR-085.
  6. All `emit` remains pull-based/consumer-driven per EDR-021/EDR-050/EDR-091; no push-based
     `emit` mode is specified anywhere in the language.
  7. The emit-applicability criterion and the compiler-diagnostic recommendation are documented in
     `what/concepts/EMIT_AS_INTERMEDIATE_RESULT.md` (done by Task 2 of this plan).

# Phase 04.1: Concepts Human's Verification - Research

**Researched:** 2026-08-03
**Domain:** Documentation verification and governance remediation (Markdown-only, no code/tools)
**Confidence:** HIGH

## Summary

Phase 04.1 is a systematic verification of 49 accepted concept files in `what/concepts/` against a 5-point checklist, combined with closure of 8 governance debts (G1-G8) catalogued prior to this phase. The work is entirely documentation-only: reading existing Markdown files, checking them against reference documents (PRIMITIVE_BLOCKS.md, DESIGN_PRINCIPLES.md, SEMANTIC_MODEL.md), and producing a VERIFICATION-LOG.md with WARN/FAIL entries plus required actions.

The phase is organized into 18 plans: one pre-step (04.1-00: G6 consolidation), 16 verification batch (VB) plans grouped into 4 waves with inter-wave dependencies, and one governance sync plan (04.1-17). The VB batches are user-authored and locked (D-07). Verification is non-blocking (D-01): FAIL entries accumulate and are resolved in the governance plan (04.1-17), not inline per batch.

**Primary recommendation:** Each VB plan should read its batch's concept files, check each concept against the 5-point checklist (Primitive Block decomposition, intra-batch consistency, cross-batch references, EDR Alternatives quality, DESIGN_PRINCIPLES.md alignment), produce a batch section in VERIFICATION-LOG.md, and flag WARN/FAIL entries per D-02/D-03 severity rules. The governance plan (04.1-17) then processes all accumulated FAILs and updates registries.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**D-01: Verification fail behavior -- non-blocking.** A failing concept does NOT halt the current wave. The agent records the failure and continues. The final governance plan (plan 17/18) processes all accumulated FAIL entries.

**D-02: VERIFICATION-LOG.md -- severity + required action format.** Each entry follows: `| Concept | Check-point | Severity | Required Action |`. WARN = issue exists but does not prevent Phase 5. FAIL = must be resolved before Phase 5.

### Anti-Patterns to Avoid

- **Blocking on WARN:** Per D-01, never halt batch processing on a WARN finding. Record and continue. Only FAILs (two conditions per D-03) are blocking, and even those are handled in plan 17, not inline.
- **Re-designing concepts during verification:** Phase 4.1 verifies what exists. If a concept needs redesign, it gets a WARN/FAIL entry with a required action for Phase 4.2 or Phase 5. The verifier does not modify concept semantics.
- **Applying D-04 (Policy) rules to non-Policy concepts:** Only the 5 explicitly listed concepts are exempt from `what/concepts/` file requirement. All other concepts must have a concept file.
- **Conflating CONCURRENCY_MODEL and CONCURRENCY:** CONCURRENCY_MODEL (EDR-033, Language-level) has a concept file. CONCURRENCY (EDR-049, StdLib-level) does not. G1 refers to CONCURRENCY (the StdLib utilities file), not CONCURRENCY_MODEL.

## Common Pitfalls

### Pitfall 1: Misidentifying FAIL vs. WARN

**What goes wrong:** A verifier marks a "stale cross-reference" or "thin Alternatives section" as FAIL, creating unnecessary blockers for Phase 5.
**Why it happens:** The two FAIL conditions (D-03) are narrow -- only "missing EDR" and "missing concept file when EDR exists." Everything else is WARN. Without explicit reference to D-03, agents default to FAIL.
**How to avoid:** Every VB plan must reference D-03 explicitly and check FAIL conditions before any other checks. If neither FAIL condition is met, the maximum severity is WARN.
**Warning signs:** A VERIFICATION-LOG.md with many FAIL entries (more than the 4 known G1/G3 items).

### Pitfall 2: Wrong Concept File for Policy-Level Entries

**What goes wrong:** Verifier flags ALLOCATION, REGION_BASED_MEMORY_MANAGEMENT, etc. as FAIL because `what/concepts/ALLOCATION.md` does not exist.
**Why it happens:** D-04 exempts these 5 concepts from the concept-file requirement, but the verifier must know the list.
**How to avoid:** Each VB plan that contains Policy-level concepts must explicitly list them with D-04 reference and check EDR + strategy file instead.
**Warning signs:** FAIL entries for any of the 5 D-04 concepts.

### Pitfall 3: Wave Dependency Violation

**What goes wrong:** A Wave 2 plan references results from another Wave 2 plan that hasn't completed yet, or a Wave 3 plan starts before all Wave 2 batches finish.
**Why it happens:** Within-wave plans are independent, but cross-wave dependencies exist. The VERIFICATION-LOG.md from Wave N is input to Wave N+1.
**How to avoid:** Wave gate: before starting any Wave N+1 plan, verify all Wave N batch entries exist in VERIFICATION-LOG.md.
**Warning signs:** Cross-batch references in a VB plan citing concepts from the same wave that haven't been verified yet.

### Pitfall 4: CONCURRENCY vs. CONCURRENCY_MODEL Confusion

**What goes wrong:** Verifier confuses CONCURRENCY_MODEL.md (exists, Language-level, EDR-033) with CONCURRENCY.md (missing, StdLib-level, EDR-049). Reports either a false PASS or a false FAIL.
**Why it happens:** The names are similar; the concept files are in the same directory.
**How to avoid:** VB10 plan must explicitly distinguish: CONCURRENCY_MODEL = EDR-033, file exists. CONCURRENCY = EDR-049, file missing (G1 FAIL).
**Warning signs:** VB10 verification log has no entry for CONCURRENCY or confuses its EDR number.

### Pitfall 5: Reconstructed Summaries (G6) Not Matching Template

**What goes wrong:** The 4 reconstructed summaries (04-03, 04-05, 04-07, 04-08) use a different format than existing summaries, making them inconsistent.
**Why it happens:** The agent writes summaries from memory rather than studying the existing template.
**How to avoid:** Plan 04.1-00 must explicitly read one existing summary (e.g., 04-01-SUMMARY.md) as template before writing any reconstructed summary.
**Warning signs:** Reconstructed summaries missing the YAML front matter, or using different section headings.

### Pitfall 6: G2 (CONSTRAINED_TYPES in LIBRARY_BOUNDARY.md) Overlooked

**What goes wrong:** CONSTRAINED_TYPES appears in CORE_CONCEPTS.md (3 references found) but is missing from LIBRARY_BOUNDARY.md (0 references). The governance plan omits adding it.
**Why it happens:** CONSTRAINED_TYPES was processed late (EDR-080) and missed the LIBRARY_BOUNDARY.md update.
**How to avoid:** Plan 04.1-17 must explicitly check LIBRARY_BOUNDARY.md for every concept that has an EDR, not just for the known G2 item. The G2 gap is confirmed (grep returns 0 matches).
**Warning signs:** LIBRARY_BOUNDARY.md still has 0 CONSTRAINED_TYPES entries after governance sync.

### 5-Point Checklist Application (per concept)

```markdown
<!-- Template for each concept's verification -->

### [CONCEPT_NAME] -- Verification

**1. Primitive Block Decomposition**
- [ ] Concept decomposes onto the 9-primitive set in PRIMITIVE_BLOCKS.md
- [ ] Decomposition path documented (which primitives, how composed)
- [ ] No new primitives required

**2. Intra-batch Consistency**
- [ ] No semantic conflicts with other concepts in this VB batch
- [ ] Shared terminology matches GLOSSARY.md definitions
- [ ] No overlapping responsibility with batch-mates

**3. Cross-batch References**
- [ ] All See-also links resolve to existing files
- [ ] Referenced concepts in other batches are consistent in their claims
- [ ] No circular semantic dependencies that violate the wave ordering

**4. EDR Alternatives Quality**
- [ ] EDR has an Alternatives section
- [ ] Alternatives are substantive (not "none considered" or single-line stubs)
- [ ] Each alternative has a stated reason for rejection

**5. DESIGN_PRINCIPLES.md Alignment**
- [ ] Concept does not violate any of the 22 Design Principles
- [ ] Concept explicitly serves at least one principle (traced in EDR)
- [ ] No tension with locked principles (flagged as WARN if tension exists)
```

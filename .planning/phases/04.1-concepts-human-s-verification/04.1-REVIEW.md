# Phase 04.1: Code Review Report

**Reviewed:** 2026-08-04T14:30:00Z
**Depth:** standard
**Files Reviewed:** 14
**Status:** issues_found

## Summary

Phase 04.1 produced 14 changed files across four categories: 3 research
concept documents (OP_DISPATCH, SCOPED_RESOURCE_LIFECYCLE expansion,
VOLDEMORT_TYPES), 2 tooling documents (LANGUAGE_SERVER, README update), 3
notes (ABI, C ABI interop, LLVM relationship), 4 new accepted concept
specification files (CONCURRENCY, PUSH_STREAMS, OBJECT_INITIALIZATION,
REQUIRE_USING_DEPENDENCY_SLOTS), and updates to the two registry files
(CORE_CONCEPTS.md, LIBRARY_BOUNDARY.md).

The research documents (OP_DISPATCH, VOLDEMORT_TYPES, SCOPED_RESOURCE_LIFECYCLE)
demonstrate strong analytical depth -- thorough comparative analysis across
multiple languages, well-structured pipeline evaluation, and clear deferral
rationale. The tooling documents (LANGUAGE_SERVER, README) and notes (ABI,
C ABI interop, LLVM) are clean and correctly cross-referenced. The four new
concept specification files are individually template-compliant.

However, the registry-side integration is materially incomplete and internally
contradictory: CORE_CONCEPTS.md claims 53 accepted concepts but only
enumerates 49; LIBRARY_BOUNDARY.md omits one of the four new concepts entirely
and has a blockquote that breaks its classification table; and every one of
the four new concept files links to its accepting EDR via a broken relative
path. Additionally, all three new research documents carry broken relative
links to DESIGN_PRINCIPLES.md. In a documentation-only codebase where
cross-references are the primary navigation mechanism, broken links are
functional defects equivalent to null pointer dereferences in code.

## Critical Issues

### CR-01: CORE_CONCEPTS.md registry claims 53 concepts but only registers 49

**File:** `what/CORE_CONCEPTS.md:8-10`
**Issue:** The status banner states: "53 concepts accepted (49 Phase 4
accepted concept files plus 4 governance-completion concept files created
in Phase 4.1: CONCURRENCY, PUSH_STREAMS, OBJECT_INITIALIZATION,
REQUIRE_USING_DEPENDENCY_SLOTS)." However, the document body (the actual
registry entries, from `## Wave 1` through `## Post-Phase 4 Additions`)
contains exactly 49 `###` heading entries. None of the four Phase 4.1
concepts appear as their own registry row anywhere in the file.
`CONCURRENCY_MODEL` (EDR-033, a different pre-existing concept) is present,
but `CONCURRENCY` (EDR-049), `PUSH_STREAMS` (EDR-051),
`OBJECT_INITIALIZATION` (EDR-054), and `REQUIRE_USING_DEPENDENCY_SLOTS`
(EDR-081) have zero registry entries. CORE_CONCEPTS.md is documented as the
canonical "REGISTRY" of accepted concepts; as written, a reader cannot
locate the four Phase 4.1 concepts in it, cannot see their EDR number,
classification, or spec-file link from the registry, and the "53 concepts
accepted" claim is unsupported by the document's own content.
**Fix:** Add registry entries for the four missing concepts (matching the
existing table format: Status / EDR / Specification / Classification /
Summary / Primitive Decomposition), most naturally under a new section:

```markdown
## Phase 4.1 -- Governance Completion

### CONCURRENCY

| Field | Value |
|-------|-------|
| **Status** | Accepted |
| **EDR** | [EDR-049](../../how/decision_records/architecture/EDR-049-concurrency.md) |
| **Specification** | [`concepts/CONCURRENCY.md`](concepts/CONCURRENCY.md) |
| **Classification** | StdLib (D-03) |
| **Summary** | StdLib concurrency utilities built on the delegate model (EDR-033): typed channels, select expressions, supervision trees, fan-out/fan-in patterns. No new language semantics. |
| **Primitive Decomposition** | All utilities decompose to delegate primitives + standard library types. No new compiler semantics. |
```

Repeat for PUSH_STREAMS (EDR-051), OBJECT_INITIALIZATION (EDR-054), and
REQUIRE_USING_DEPENDENCY_SLOTS (EDR-081).

### CR-03: All 4 Phase 4.1 concept files link to their accepting EDRs via broken relative paths

**File:** `what/concepts/CONCURRENCY.md:3`,
`what/concepts/PUSH_STREAMS.md:3`,
`what/concepts/OBJECT_INITIALIZATION.md:3`,
`what/concepts/REQUIRE_USING_DEPENDENCY_SLOTS.md:5,11`
**Issue:** Each file's opening banner links to its EDR using
`../how/decision_records/architecture/EDR-NNN-*.md`. These files live in
`what/concepts/`; `how/` is a sibling of `what/` at the repo root, so
escaping `what/concepts/` to reach it requires two `../` segments, not one.
As written, `../how/...` resolves to `what/how/decision_records/...`, which
does not exist. Verified directly:

```
$ ls what/concepts/../how/decision_records/architecture/EDR-049-concurrency.md
No such file or directory
$ ls what/concepts/../../how/decision_records/architecture/EDR-049-concurrency.md
exists
```

This is the single most load-bearing link in each document -- the proof that
the concept was actually accepted -- and it 404s in every file under review.
Note: this same pattern also exists in pre-existing Phase 4 concept files
(EQUALITY.md, TRAITS.md, etc.); the 4 new files replicate the existing bug.

**Fix:** Add a second `../` to every `how/`-rooted link in these four files:

```diff
- [EDR-049](../how/decision_records/architecture/EDR-049-concurrency.md)
+ [EDR-049](../../how/decision_records/architecture/EDR-049-concurrency.md)
```

Apply to all four files plus the "Refines" link to EDR-037 in
REQUIRE_USING_DEPENDENCY_SLOTS.md:11. Recommend a follow-up bulk fix across
all `what/concepts/*.md` for the pre-existing instances.

### WR-06: `using` resolution syntax differs between function calls and constructors without explanation

**File:** `what/concepts/REQUIRE_USING_DEPENDENCY_SLOTS.md:69-90`
**Issue:** The "Model" section shows two syntactically different positions for
the same `using` keyword:

```orthon
// function call -- postfix clause after closing paren
process(42) using prod_db, prod_log

// constructor call -- inside the call parens
let prod_svc = UserService(using prod_db, prod_log)
```

No principle or rule in the document explains why the keyword attaches
differently. Given the project's explicit LLM Generability Gate requirement,
an unexplained syntactic fork risks incorrect code generation -- a model is
equally likely to produce `UserService(prod_db, prod_log) using` or
`process(42, using prod_db, prod_log)` since nothing in the spec
distinguishes the two forms.
**Fix:** Either unify the two forms (e.g. always postfix or always inline),
or add an explicit rule to the "Model" section stating the syntactic
distinction and its rationale.

# Phase 04.1: Code Review Report

**Reviewed:** 2026-08-04T11:57:08Z
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

This phase's stated purpose is to close out governance gaps by adding four
Phase-4.1 concept files (CONCURRENCY, PUSH_STREAMS, OBJECT_INITIALIZATION,
REQUIRE_USING_DEPENDENCY_SLOTS) and reconciling them into the two registry
documents (`CORE_CONCEPTS.md`, `LIBRARY_BOUNDARY.md`). The four concept files
themselves are individually well-formed and template-compliant (Issue →
Principles → Policy Footprint → Model → Default Strategy → Alternative
Strategies → Open Questions → Decision History, in the correct order), but
the registry-side integration is materially incomplete and internally
contradictory, and every one of the four new concept files carries a broken
relative-path link to its own accepting EDR — the exact citation a reader
would follow to verify the "Accepted" claim. None of this was caught by a
surface read; it required cross-checking the header prose against the actual
table contents, and testing the relative paths from each file's own
directory.

Three verified defects are severe enough to block sign-off (registry claims
53 accepted concepts but only enumerates 49; one of the four new concepts is
missing from the classification aggregate entirely, producing an
irreconcilable count mismatch; and the EDR citation links in all four new
concept files 404). Four further defects degrade the registry's reliability
as a source of truth and should be fixed before this phase is considered
closed.

## Critical Issues

### CR-01: CORE_CONCEPTS.md registry is missing table entries for the 4 concepts it claims to add

**File:** `what/CORE_CONCEPTS.md:9-11`
**Issue:** The document's status banner says: "53 concepts accepted (49 Phase
4 accepted concept files plus 4 governance-completion concept files created
in Phase 4.1: CONCURRENCY, PUSH_STREAMS, OBJECT_INITIALIZATION,
REQUIRE_USING_DEPENDENCY_SLOTS)." However, the document body (the actual
registry table rows, `## Wave 1` through `## Post-Phase 4 Additions`)
contains exactly 49 concept entries — confirmed by grep — and none of the
four named concepts appear as their own registry row anywhere in the file.
`CONCURRENCY_MODEL` (a different, pre-existing concept) is present, but
`CONCURRENCY`, `PUSH_STREAMS`, `OBJECT_INITIALIZATION`, and
`REQUIRE_USING_DEPENDENCY_SLOTS` have zero table rows. `CORE_CONCEPTS.md` is
documented as the canonical "REGISTRY" of accepted concepts; as written, a
reader cannot locate the four Phase 4.1 concepts in it, cannot see their EDR
number, classification, or spec-file link from the registry, and the "53
concepts accepted" claim is unsupported by the document's own content.
**Fix:** Add registry rows for the four concepts (matching the existing
table format used by every other entry — Status / EDR / Specification /
Classification / Summary / Primitive Decomposition), most naturally under a
new `## Phase 4.1 — Governance Completion` section:
```markdown
## Phase 4.1 — Governance Completion

### CONCURRENCY

| Field | Value |
|-------|-------|
| **Status** | Accepted |
| **EDR** | [EDR-049](../how/decision_records/architecture/EDR-049-concurrency.md) |
| **Specification** | [`concepts/CONCURRENCY.md`](concepts/CONCURRENCY.md) |
| **Classification** | StdLib (D-03) |
| **Summary** | ... |

... (repeat for PUSH_STREAMS / EDR-051, OBJECT_INITIALIZATION / EDR-054,
REQUIRE_USING_DEPENDENCY_SLOTS / EDR-081)
```

### CR-02: LIBRARY_BOUNDARY.md omits REQUIRE_USING_DEPENDENCY_SLOTS entirely, and the aggregate counts no longer reconcile

**File:** `what/LIBRARY_BOUNDARY.md:18-28`
**Issue:** `REQUIRE_USING_DEPENDENCY_SLOTS` — one of the four Phase 4.1
concepts this phase is meant to close out — does not appear anywhere in
`LIBRARY_BOUNDARY.md` (verified with `grep -n "REQUIRE_USING\|DEPENDENCY_SLOT"`,
zero hits). It is absent from the Language list (36 items), the Standard
Library list (16 items), and the by-tier breakdown sections. Its own spec
file states its classification plainly: "Classification: Language Pattern
(Level 2)" — the same tier as `CONSTRAINED_TYPES`, which *was* correctly
added to the Language list with an explicit G2 changelog note
(`what/LIBRARY_BOUNDARY.md:21-23`). No equivalent note or list entry exists
for `REQUIRE_USING_DEPENDENCY_SLOTS`.

This produces a direct arithmetic contradiction with `CORE_CONCEPTS.md`:
Language (36) + Standard Library (16) = 52, but `CORE_CONCEPTS.md:9`
claims 53 concepts accepted. Adding `REQUIRE_USING_DEPENDENCY_SLOTS` to the
Language count (37) makes 37 + 16 = 53, which is the only way the two
documents' totals reconcile — confirming this is an omission, not a
deliberate exclusion.
**Fix:** Add `REQUIRE_USING_DEPENDENCY_SLOTS` to the Language row (making it
37) with a G2-style note mirroring the existing CONSTRAINED_TYPES note, and
add it to the "Important Tier — Language" breakdown list:
```markdown
| **Language** | 37 | ..., CONSTRAINED_TYPES, REQUIRE_USING_DEPENDENCY_SLOTS |
> **Note (G2, 2026-08-04):** REQUIRE_USING_DEPENDENCY_SLOTS added to the
> Language category per EDR-081 (Language Pattern, Level 2), closing the
> second G2 registry gap identified in Phase 4.1 verification.
```

### CR-03: Every Phase 4.1 concept file links to its accepting EDR with a broken relative path

**File:** `what/concepts/CONCURRENCY.md:3`, `what/concepts/PUSH_STREAMS.md:3`,
`what/concepts/OBJECT_INITIALIZATION.md:3`,
`what/concepts/REQUIRE_USING_DEPENDENCY_SLOTS.md:3,11`
**Issue:** Each file's opening "✅ ACCEPTED" banner links to its EDR using a
path of the form `../how/decision_records/architecture/EDR-NNN-....md`. These
files live in `what/concepts/`; `how/` is a sibling of `what/` at the repo
root, so escaping `what/concepts/` to reach it requires **two** `../`
segments, not one. As written, `../how/...` resolves to
`what/how/decision_records/...`, which does not exist — verified directly:
```
$ ls what/concepts/../how/decision_records/architecture/EDR-049-concurrency.md
ls: what/concepts/../how/...: No such file or directory
$ ls what/concepts/../../how/decision_records/architecture/EDR-049-concurrency.md
what/concepts/../../how/decision_records/architecture/EDR-049-concurrency.md   # exists
```
This is the single most load-bearing link in each document — it's the proof
that the concept was actually accepted — and it 404s in every one of the
four files under review. (Note: this same one-`../`-too-few pattern also
exists in several pre-existing Phase-4 concept files, e.g.
`what/concepts/TRAITS.md:3` — it is not unique to Phase 4.1, but all four
files in this review's scope inherit the bug.)
**Fix:** Add a second `../` to every `how/`-rooted link in these four files:
```diff
- > **✅ ACCEPTED — [EDR-049](../how/decision_records/architecture/EDR-049-concurrency.md).**
+ > **✅ ACCEPTED — [EDR-049](../../how/decision_records/architecture/EDR-049-concurrency.md).**
```
Apply the same fix to `PUSH_STREAMS.md` (EDR-051), `OBJECT_INITIALIZATION.md`
(EDR-054), and `REQUIRE_USING_DEPENDENCY_SLOTS.md` (EDR-081 and its
"Refines" link to EDR-037). Recommend a follow-up grep across all of
`what/concepts/*.md` for `](../how/` to catch the pre-existing instances
too, since they share the same defect.

### WR-01: CORE_CONCEPTS.md "Wave" heading numbering contradicts its own header prose

**File:** `what/CORE_CONCEPTS.md:22-25` vs `what/CORE_CONCEPTS.md:260,341,481`
**Issue:** The header prose states: "Wave 5 concepts (ALGEBRAIC_DATA_TYPES
through TYPE_LEVEL_COMPUTATION, EDR-039–046) registered separately." But the
section heading that actually contains ALGEBRAIC_DATA_TYPES through
TYPE_LEVEL_COMPUTATION (EDR-039 through EDR-046) is literally titled
`## Wave 4 — Important Tier (Phase 4)` (line 260) — not "Wave 5". A second,
unrelated section (ASYNC_AWAIT through UNPACKING, EDR-047–055) is *also*
titled `## Wave 4 — Important Tier (Phase 4)` (line 341) — the same heading
text used twice for two disjoint concept sets. A third section (SLOTS
through DECLARATION_BY_ASSIGNMENT, EDR-063–074, 12 concepts) is titled
`## Wave 4 — Important Tier (Phase 4, Batch 2)` (line 481) and *does* match
the header's "Wave 4 (important tier: 12 concepts)" claim (line 13). Neither
"Wave 3" nor "Wave 5" ever appears as an actual `##` heading in the document,
despite both being referenced by name in the header. A reader trying to
locate "Wave 5" per the header's own instructions will not find a
"Wave 5" heading anywhere in the file.
**Fix:** Rename the heading at line 260 to `## Wave 5 — Important Tier
(Phase 4)` to match the header prose and the EDR-039–046 range, and rename
the heading at line 341 to a distinct, non-colliding label (e.g. `## Wave 4a`
or fold it into the "Wave 4, Batch 2" section it precedes) so that "Wave 4"
is used consistently for one specific concept group across both the header
summary and the section headings.

### WR-02: GLOSSARY.md cross-references in all four Phase 4.1 concept files point to non-existent terms

**File:** `what/concepts/CONCURRENCY.md:13`, `what/concepts/PUSH_STREAMS.md:14`,
`what/concepts/OBJECT_INITIALIZATION.md:14`,
`what/concepts/REQUIRE_USING_DEPENDENCY_SLOTS.md:15`
**Issue:** Each file's "See also" block cites `GLOSSARY.md` sections that do
not exist:
- `CONCURRENCY.md` → "§ Channel, Delegate" — `GLOSSARY.md` has `### Delegate`
  (line 253) but **no** `Channel` entry anywhere in the file.
- `PUSH_STREAMS.md` → "§ Stream" — **no** `Stream` entry anywhere in
  `GLOSSARY.md`.
- `OBJECT_INITIALIZATION.md` → "§ Default Value, Named Parameter" — neither
  term exists as a heading; the closest match is `### Named and Optional
  Parameters` (line 1176), a different term.
- `REQUIRE_USING_DEPENDENCY_SLOTS.md` → "§ Context Parameter, Dependency
  Slot" — **neither** term exists anywhere in `GLOSSARY.md` (confirmed with
  `grep -n "Context Parameter\|Dependency Slot" what/GLOSSARY.md` → no
  output).

This violates the project's own Terminology Consistency rule
(`.claude/CLAUDE.md`: "New terms introduced in any concept document must be
added to `what/GLOSSARY.md`... enforcement: before creating or modifying any
file, agent MUST confirm every string is English" and "All project
terminology defined in `what/GLOSSARY.md`... terms used consistently").
`Channel`, `Stream`, `Dependency Slot`, and `Context Parameter` are all
load-bearing terms used repeatedly in their respective concept bodies (e.g.
`Channel<T>` and `select` throughout `CONCURRENCY.md`) but were never
promoted to the glossary despite the cross-reference implying they were.
**Fix:** Either add the six missing terms (`Channel`, `Stream`, `Default
Value`, `Named Parameter`, `Context Parameter`, `Dependency Slot`) as
`### `-level entries in `GLOSSARY.md` with definitions and back-links to
their source documents, or correct the "See also" citations to point at
terms that actually exist (e.g. `§ Delegate` only for CONCURRENCY.md, `§
Named and Optional Parameters` for OBJECT_INITIALIZATION.md).

### WR-03: LIBRARY_BOUNDARY.md's top-level Status line is stale relative to its own body

**File:** `what/LIBRARY_BOUNDARY.md:10`
**Issue:** The document header reads "**Status:** Finalized — Phase 4
complete." This was written before the Phase 4.1 additions and was only
partially patched afterward (a G2 note was added for `CONSTRAINED_TYPES` at
line 21-23, and the Standard Library row was updated in-place to include
`CONCURRENCY`, `PUSH_STREAMS`, `OBJECT_INITIALIZATION`). The top-level Status

**Fix:**

```diff
+ **Status:** Finalized — Phase 4 complete; Phase 4.1 governance-completion

```
Apply after CR-02 is fixed, so the status statement is actually true.

### WR-04: `using` resolution syntax differs between function calls and constructors without explanation

**File:** `what/concepts/REQUIRE_USING_DEPENDENCY_SLOTS.md:69-90`
**Issue:** The "Model" section shows two different syntactic positions for
the same `using` resolution keyword:
```orthon
// function call — `using` is a trailing postfix clause
process(42) using prod_db, prod_log

// constructor call — `using` is nested inside the call parens
let prod_svc = UserService(using prod_db, prod_log)
```
No principle, rule, or open question in the document explains why the same
keyword attaches differently depending on whether the callee is a function
or a constructor. Given this project's explicit LLM Generability Gate
requirement (`.claude/CLAUDE.md`: "every language construct must pass the
LLM Generability Gate"), an unexplained syntactic fork for the same keyword
is exactly the kind of inconsistency that risks incorrect code generation —
a model is equally likely to write `UserService(prod_db, prod_log) using`
or `process(42, using prod_db, prod_log)` since nothing in the spec rules
either out.
**Fix:** Either unify the two forms (e.g. always postfix:
`UserService() using prod_db, prod_log`, or always inline), or add an
explicit rule to the "Model" section stating the syntactic distinction and
why it exists (e.g. "constructor `using` is part of the call argument list
because construction has no post-call site; function `using` is postfix to
keep the data-argument list visually separate from the context-argument
list").

## Info

### IN-01: `@builder` macro referenced but never defined or cross-referenced anywhere else

**File:** `what/concepts/OBJECT_INITIALIZATION.md:42,70`
**Issue:** The document asserts "Builder auto-generation is provided via the
`@builder` macro (AST macros, EDR-029)" and shows a `@builder` annotation
example, but `@builder` does not appear anywhere else in `what/` (checked
`AST_MACROS.md` and `DATACLASSES.md`, the two documents that define the
actual registered macro vocabulary — `@macro`, `@derive(init, eq, repr,
hash)`). Unlike `@derive`, which is consistently defined and cross-linked
across multiple accepted concept files, `@builder` is introduced here as if
pre-existing but has no defining document.
**Fix:** Either add `@builder` to the macro registry described in
`AST_MACROS.md` (or as a `@derive(builder)` variant consistent with
`DATACLASSES.md`'s pattern), or rephrase to make clear this is a proposed
StdLib macro introduced by this document rather than a reference to an
already-established one.

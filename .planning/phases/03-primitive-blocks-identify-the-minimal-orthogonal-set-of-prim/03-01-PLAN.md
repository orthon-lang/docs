    **1. Purpose & Scope** — Brief statement that this is the Level 1 (Primitive Operations) layer of the Semantic Dependency Architecture, replacing the DRAFT. Every construct decomposes into these. Link to SEMANTIC_MODEL.md (the semantic dimensions these primitives serve) and ROADMAP.md (Phase 4 depends on this being settled).

    **2. Organizing Taxonomy** — State per D-02 that Data/Data Modifiers (from FOUNDATIONAL_ABSTRACTIONS.md) serve as the conceptual organizing framework, not the primitive set itself. Primitives are categorized as "Data primitives" and "Data Modifier primitives."

    **3. Primitive Specifications** — For each primitive, provide:
    - Name and one-sentence definition
    - Category (Data or Data Modifier)
    - Semantic dimensions served (which of the 6 SEMANTIC_MODEL.md dimensions this primitive addresses, with explanation)
    - Orthogonality statement (what it does NOT overlap with)
    - Composition rules (how it combines with other primitives)
    - Code examples in abstract Orthon syntax (using `orthon` code blocks)

    The validated primitive set (derived from the 11-item hypothesis per D-01..D-10 adjustments):

    **Data Primitives (3 conceptual primitives):**
    1. **literal** — Inline value notation. Produces a Data value from source text. Serves: Data (directly creates data). Orthogonal to: identifier (no binding), assignment (no storage). Composition: produces values consumed by assignment, function arguments, pack, etc.
    2. **identifier** — Named reference to a value. Binds a name to a storage location holding a value. Serves: Identity (names the binding point), Ownership (the named binding is the owner of the value). Orthogonal to: literal (names vs. values), scope (names exist within scopes but are not the scope itself). Composition: every named construct (function, variable, type) uses identifier.
    3. **pack/unpack** — Symmetric composition/decomposition pair (one primitive, two operations). pack combines values into a composite structure; unpack decomposes a composite into its constituent values. Serves: Data (construction/destruction), Representation (the composite's structure). Orthogonal to: literal (pack combines existing values, literal creates from scratch), reference (pack is structural, not indirection). Composition: pack underlies struct, tuple, and record construction; unpack underlies destructuring assignment and pattern matching. Per D-01 and UNPACKING.md symmetry principle: construction and destruction follow the same syntax.

    **Data Modifier Primitives (6 conceptual primitives):**
    4. **assignment** — Bind a value to an identifier. Creates or updates a binding between a name and a storage location holding a value. Serves: Evaluation (stores a value for later use), Ownership (establishes ownership of the value at the binding point). Orthogonal to: identifier (identifier names the slot, assignment fills it). Composition: let/var declarations, parameter binding, field assignment all decompose to assignment.
    5. **function** — Parameterized computation declaration. Defines a reusable computation with explicit parameters and an optional return type. Serves: Evaluation (declares a computation boundary). Per D-04: The three declaration kinds (fun/proc/new) are tags on the function primitive, not separate primitives — they modify how the function interacts with its context (pure, mutating, transforming). Orthogonal to: call (declaration vs. invocation is the split). Composition: function bodies are scope + assignment + other primitives; closures decompose to function + identifier + scope (captured environment).
    6. **call** — Invocation of a declared function. Triggers evaluation of a function body with supplied arguments. Unified syntax regardless of declaration form (named, anonymous, closure). Serves: Evaluation (triggers computation), Lifetime (function scope begins at call and ends at return). Orthogonal to: function (declaration vs. invocation). Composition: every function execution is a call; recursion is call composed with itself.
    7. **attribute access** — Access a member of a composite value. Dereferences a named field or method on a composite. Uses `.` syntax. Serves: Visibility (selects which part of a composite to expose). Orthogonal to: reference (attribute access selects, reference points), pack/unpack (attribute access extracts a single named member; unpack extracts multiple by structure). Composition: field reads, method calls, chained access all decompose to attribute access.
    8. **scope** — Lexical boundary for names and lifetimes. Defines a region where bindings are valid, lifetimes are determined, and visibility is contained. Serves: Visibility (names are visible only within their scope), Lifetime (values live until scope exit per Semantic Invariant 3). Orthogonal to: all other primitives (scope is the container, not an operation). Composition: function bodies, block statements, module boundaries all define scopes. Per D-09: { } blocks require explicit return; expression-level constructs (if, match, when) use last-expression-as-value.
    9. **reference** — Indirection to a value without ownership transfer. Creates a handle that points to an existing value without claiming ownership. Serves: Ownership (borrowing mechanism), Lifetime (reference lifetime ≤ referent lifetime). Per D-10: Whether shared (&T) and exclusive (&mut T) are one primitive or two is documented as an open question resolved below — they are ONE primitive (reference) with two modes: shared (read-only) and exclusive (mutable). Interior mutability (Cell/RefCell patterns) is NOT a primitive — it is a derived feature composed of reference + mutation semantics, deferrable to the Standard Library. Orthogonal to: pack (reference points to a value, pack combines values), assignment (reference does not create a new binding, it aliases an existing one). Composition: function parameters use reference for borrowing; class identity semantics build on reference.

    **4. Exclusions and Decomposition** — For each excluded concept, document HOW it decomposes into primitives, with rationale and source reference:

    | Excluded Concept | Decomposition | Source |
    |---|---|---|
    | `operator definition` | Syntactic sugar for `function` with a symbolic name | D-01, DESIGN_PRINCIPLES.md § Named Before Symbolic |
    | `struct` | Type-level convenience for `pack` + `identifier` + `scope` | D-03, STRUCT_AS_VALUE_TYPE.md |
    | `class` | Type-level convenience for `pack` + `reference` + `scope` + assignment | D-03, CLASS_WITH_ACT.md |
    | `delegate` | Execution policy composing `reference` + `function` + ownership | D-05, DELEGATE.md |
    | `namespace` | Organizational convenience: `identifier` + `scope` + visibility | D-05, NAMESPACES.md |
    | `act` (isolation) | Concurrency modifier on `function` tag, built on `reference` + scope | CLASS_WITH_ACT.md |
    | `act` fields | `reference` + scope (isolated access) | CLASS_WITH_ACT.md |

    **5. D-10 Resolutions** — Document these open items as settled for the primitive set:

    - **Interior mutability (Cell/RefCell):** NOT a primitive. It is a derived Standard Library feature (or Implementation Strategy concern) built on `reference` + mutation semantics. The reference primitive provides the indirection; interior mutability is a runtime pattern layered on top, not an irreducible atomic operation. The primitive set is complete without it.
    - **Mutation in closures:** Closures capture variables as immutable by default. Explicit `mut` on the captured binding is required for mutable capture, consistent with the overall immutability-by-default model (SEMANTIC_MODEL.md § Mutation, Immutable by default).
    - **`mut` vs `&mut`:** One keyword (`mut`) serves both binding-level and reference-level mutation marking. `mut x` at binding site declares a mutable binding; `&mut` is the reference's mutation mode (part of the reference primitive's two-mode design). The semantic distinction (mutable binding vs. mutable reference) is separate from the keyword count; one keyword suffices for both, consistent with Explicitness (both are visible at their sites).

    **6. Metadata Protocol** — Define the `@` prefix convention per D-07. `@` is not a primitive — it is a syntactic marker for metadata access on types and values. Examples: `list@len()`, `obj@fields`, `type@name`. The `@` prefix makes metadata access syntactically distinct from attribute access (`.`) per Semantic Purity.

    **7. emit Lazy by Default** — Document per D-06: `emit` produces values on demand (lazy). Eager sequence production uses `return` with an aggregate collection. Cross-reference to SEMANTIC_MODEL.md § Evaluation.

    **8. Composition Rules** — Document how primitives combine:
    - Primitives compose by nesting (one primitive's output feeds another's input)
    - No primitive requires another primitive to be meaningful (orthogonality)
    - The composition of primitives is the definition of a derived feature
    - If a derived feature cannot be decomposed, revisit this set before Phase 4

    Add the following new entries to `what/GLOSSARY.md` in alphabetical order:

    1. **Composition (of primitives)** — The process by which multiple primitive operations combine to produce a derived language feature. A feature is well-formed when its decomposition into primitives is unique and does not require additional semantics beyond what the primitives provide. Source: `../what/PRIMITIVE_BLOCKS.md` § Composition Rules.

    2. **Data Primitive** — A primitive block whose primary responsibility is producing or structuring data values. The three Data primitives are `literal` (value creation), `identifier` (value naming), and `pack/unpack` (value composition/decomposition). Distinguished from Data Modifier Primitives which transform or access data rather than constructing it. Source: `../what/PRIMITIVE_BLOCKS.md`.

    3. **Data Modifier Primitive** — A primitive block whose primary responsibility is transforming, accessing, or controlling data rather than constructing it. The six Data Modifier primitives are `assignment`, `function`, `call`, `attribute access`, `scope`, and `reference`. Distinguished from Data Primitives which produce or structure data. Source: `../what/PRIMITIVE_BLOCKS.md`.

    4. **Metadata Protocol** — The `@`-prefixed convention for accessing metadata and protocol methods on types and values. Examples: `list@len()`, `obj@fields`, `type@name`. Distinct from attribute access (`.`); the `@` prefix makes metadata access syntactically visible per Semantic Purity. Source: `../what/PRIMITIVE_BLOCKS.md` § Metadata Protocol.

    5. **Primitive Block** — An irreducible atomic language operation from which all constructs are composed. Each primitive serves one or more Semantic Dimensions (Identity, Ownership, Mutation, Evaluation, Visibility, Lifetime) and must be orthogonal to all other primitives (no overlap in responsibility). The complete set is defined in `../what/PRIMITIVE_BLOCKS.md`. Source: `../what/PRIMITIVE_BLOCKS.md`.

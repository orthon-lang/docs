    **ASYNC_AWAIT and ASYNC_AS_EXPLICIT_MODIFIER:**
    - Per Claude's discretion and CONTEXT.md's note that closely related concepts may share a combined EDR: ASYNC_AWAIT and ASYNC_AS_EXPLICIT_MODIFIER are two facets of the same async model. A combined EDR is recommended.
    - ASYNC_AWAIT classification: Language — async/await requires compiler-level state machine generation (the function body is rewritten into a state machine), not expressible via primitives.
    - ASYNC_AS_EXPLICIT_MODIFIER classification: Language — modifier is specifically about async being an explicit annotation on `fun`/`proc`/`new` declarations, not an implicit runtime choice. This is a semantic commitment about explicitness (per DESIGN_PRINCIPLES.md § Explicitness).
    - Design decisions: `async` is a declaration modifier, not a return type. `await` is an expression that suspends the current async context.

    **CONCURRENCY:**
    - Classification per D-03: Claude's discretion — this defines concrete concurrent execution patterns (task spawning, joining, cancelling) on top of CONCURRENCY_MODEL's delegate-based isolation model. Likely StdLib if patterns are expressible as library functions on top of delegates. Language if the compiler must recognize concurrency primitives.
    - Dependency: CONCURRENCY_MODEL (Plan 04-03) must be settled — CONCURRENCY builds on the model.
    - Cross-reference: the CONCURRENCY_MODEL EDR should already note this relationship.
    - Note the relationship between CONCURRENCY (this plan) and CONCURRENCY_MODEL (Plan 04-03) explicitly.

    **GENERATORS:**
    - Classification per D-03: Language or StdLib — generators produce lazy sequences. If they are purely syntactic sugar over the iterator protocol + closures, they are StdLib. If they require compiler-level state machine transformation (like Python's `yield` transforms a function into a generator), they are Language.
    - Dependency: LAZY_SEQUENCE_GENERATORS (Plan 04-01) — generators are a mechanism for lazy sequence production. The `emit` keyword (lazy by default, Phase 3 D-06) is the mechanism.
    - Design decision: GENERATORS.md may be largely superseded by LAZY_SEQUENCE_GENERATORS.md's `emit`-based model. If so, note this in the EDR and consider classifying GENERATORS as alternative strategy rather than separate concept.

    For each concept, follow the full procedure. Key guidance:

    **PUSH_STREAMS:**
    - Classification per D-03: StdLib — push-based reactive streams (Observable-like) are the dual of ITERATOR_PROTOCOL's pull-based iteration. Implementable as a Standard Library pattern using delegates and callbacks. No compiler-level semantics needed.
    - Cross-reference with ITERATOR_PROTOCOL (Plan 04-01) — PUSH_STREAMS is the dual (push vs pull).

    **EMIT_AS_INTERMEDIATE_RESULT:**
    - Classification per D-03: Language — `emit` as a mechanism to yield intermediate computation results is a compiler-recognized construct (settled in Phase 3 D-06 as lazy by default). The concept doc formalizes this for the intermediate-result use case.
    - Dependency: LAZY_SEQUENCE_GENERATORS (Plan 04-01) — `emit` semantics settled.
    - All canonical forms: `emit value`, `return sequence(value)`, `return value ->` — show all three as equivalent per Show All Canonical Forms principle.

    **ITERATION_LOOP:**
    - Classification per D-03: Language or StdLib — `for` and `while` loops. If `for` is syntactic sugar over the iterator protocol (compose `call` + `scope` + `assignment`), it is StdLib. If the compiler recognizes loop constructs for optimizations (bounds checking, vectorization), it may be Language. Claude's discretion.
    - Dependency: ITERATOR_PROTOCOL (Plan 04-01) — `for x in iter` desugars to iterator protocol calls.

    **OBJECT_INITIALIZATION:**
    - Classification per D-03: StdLib — constructor patterns (named constructors, builder pattern, default values). Expressible via `function` + named parameters + default values. No new semantics.
    - Cross-reference with NAMED_AND_OPTIONAL_PARAMETERS (Plan 04-07, important tier) — initialization ergonomics depend on parameter ergonomics.

    **UNPACKING:**
    - Classification per D-03: Language — destructuring is the symmetric counterpart of `pack` (per the symmetry principle in PRIMITIVE_BLOCKS.md). The `*` operator for unpack must be recognized by the compiler for destructuring assignment and pattern matching. This is the concrete user-facing syntax for the `unpack` primitive operation.
    - Dependency: PRIMITIVE_BLOCKS.md § pack/unpack — unpack is the decomposition half of the pack/unpack symmetric pair.
    - All canonical forms: destructuring assignment, function parameter destructuring, match-arm destructuring, `let * = composite`.

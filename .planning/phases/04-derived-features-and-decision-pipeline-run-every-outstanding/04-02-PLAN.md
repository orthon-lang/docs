    For each concept, follow the full procedure from Plan 04-01 Task 1 (Pipeline → Gates → 5-step Design Review → EDR → concept doc → register → INDEX). Key concept-specific guidance:

    **GENERICS (high-risk):**
    - Classification per D-03: Language — parametric polymorphism adds new semantics (type parameterization, trait bounds) not expressible via composition of primitives; compiler must resolve monomorphization.
    - Dependency: TRAITS must be settled (Plan 04-01) — generics use trait bounds on type parameters.
    - Design decisions to address: bounded vs. unbounded type params, variance (covariant/contravariant/invariant), where-clause syntax (deferred to Phase 5), monomorphization vs. boxing strategy (deferred to Phase 7 as Implementation Strategy choice).
    - Gate validation: Pay special attention to ARCHITECTURAL_INTEGRITY_GATE (generics affect every type and function) and LLM_GENERABILITY_GATE (LLMs must reliably produce correct generic code — consider whether type inference reduces the annotation burden).
    - Cross-reference: COMPILE_TIME_EXECUTION (Plan 04-03) may provide an alternative comptime-based generics model.

    **TYPE_INFERENCE:**
    - Classification per D-03: Language — type inference is a compiler-level semantic service, not expressible via primitives.
    - Dependency: EQUALITY (Plan 04-01) settled — type unification depends on type equality semantics.
    - Design decisions: Local bidirectional inference (not global Hindley-Milner). Type annotations required at public API boundaries. Inference within function bodies is complete but not required at module boundaries.
    - Deferred to Phase 5: Concrete syntax for type annotations (`: Type` syntax).

    **TYPE_LEVEL_NULL_SAFETY:**
    - Classification per D-03: Language — null safety tracked at type level (Option&lt;T&gt; vs T) requires compiler-level tracking of nullable state.
    - Dependency: NULL_SAFETY (Plan 04-01) settled — this is the type-level enforcement mechanism for the null-safety principle.
    - Design decision: Option&lt;T&gt; is the concrete mechanism. `?T` as syntactic sugar for Option&lt;T&gt; is a Phase 5 question. The type system must track when a value is definitely non-null after a check.

    For each concept, follow the full procedure. Key concept-specific guidance:

    **PATTERN_MATCHING (high-risk):**
    - Classification per D-03: Language — pattern matching adds exhaustiveness checking, destructuring semantics, and match ergonomics not expressible via primitives; compiler must verify exhaustiveness.
    - Dependency: TRAITS (Plan 04-01) settled — patterns match against trait-implementing types.
    - Design decisions: Exhaustiveness checking required (compiler error for non-exhaustive match). Patterns can destructure pack/unpack composites. `match` is an expression (per Semantic Invariant 4). Wildcard `_` pattern for catch-all.
    - Cross-reference: SMART_CAST (Plan 04-07, important tier) — pattern matching subsumes some smart cast use cases.
    - All canonical forms shown: match on literal, match on type/trait, match on composite structure, match with guards, wildcard `_`.

    **PATTERN_MATCHING_DISPATCH:**
    - Classification per D-03: Language — multimethod dispatch adds semantic uniqueness (runtime dispatch based on multiple argument types) not expressible via single-argument pattern matching alone; compiler must resolve dispatch table.
    - Dependency: PATTERN_MATCHING + TRAITS settled.
    - Design decision: This is pattern matching applied to function dispatch — `match` on function arguments at the definition site, resolved at call site. Consider whether this should be a special syntax on function declarations or a library-level pattern (Claude's discretion per CONTEXT.md).
    - Cross-reference: COMMAND_PATTERN_VIA_DELEGATE (Plan 04-07) — pattern matching + dispatch may eliminate the command pattern entirely.

    **ERROR_UNION:**
    - Classification per D-03: Language — Zig-style `!T` error union adds compiler-level error set tracking not expressible via ERROR_HANDLING's Result&lt;T,E&gt; alone. ERROR_UNION is a concrete mechanism that builds on the Result model.
    - Dependency: ERROR_HANDLING (Plan 04-01) settled.
    - Design decision: ERROR_UNION is a more specific mechanism than general Result&lt;T,E&gt; — it provides inferred, tag-only error sets where the compiler tracks which errors a function can produce. Consider whether ERROR_UNION is a variant of Result or a separate concept (Claude's discretion). If treating them as related but distinct, the EDR should document the relationship clearly.
    - Cross-reference: note the relationship to ERROR_HANDLING's EDR.

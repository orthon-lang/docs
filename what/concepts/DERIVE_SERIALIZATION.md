# Derive Serialization

## Issue (Why)

Manually converting objects to/from JSON requires recursive code that misses fields, mishandles cyclic references, and breaks type safety. Every `to_dict()` / `to_json()` written by hand is a potential source of deserialization bugs and type errors. Orthon should eliminate manual serialization code by providing automatic serialization/deserialization for value types through trait derivation.

## Principles

1. **Automatic for value types** — Serialization is automatic for value types (records / data classes) via `@derive`.
2. **Declarative customization** — Field renaming, skipping, and format selection are declarative annotations.
3. **Parse-time validation** — Deserialization validates types at parse time, not runtime.
4. **Format-agnostic** — Support JSON and binary formats through a common trait/protocol.

## Model (What)

Serialization is derived via the existing `@derive` mechanism (EDR-029):

```orthon
@derive(Serialize, Deserialize)
@json(rename_all = "snake_case")
struct User:
    name: String
    email_address: String

# Compiler generates Serialize/Deserialize impl blocks
let json = User.to_json(user)   # {"name": "...", "email_address": "..."}
let user = User.from_json(json)?   # Result<User, SerializeError>
```

## Default Strategy

Derive Serialization is a **StdLib** concept implemented via the compiler's `@derive` macro mechanism (EDR-029). A `@derive(Serialize)` annotation registers a comptime macro that generates `to_json`/`from_json` implementations for the annotated type. The StdLib provides format backends (JSON, binary) and customization annotations.

## Alternative Strategies

| Strategy | Description |
|---|---|
| Manual serialization | Every type implements its own `to_json`/`from_json`. Error-prone and repetitive. |
| Runtime reflection | Serialization via runtime type inspection. Works but bypasses compile-time guarantees. |
| External code generation | Serializers generated by a separate build step. Fragile — builds may drift from source. |

## Open Questions

1. Should serialization support binary formats in v0.1 or only JSON?
2. How to handle serialization of types with private fields?
3. Should cyclic references be supported via reference tracking?

## Decision History

- **EDR-070:** Derive Serialization accepted as StdLib — `@derive(Serialize)` pattern via comptime macro. Uses the existing `@derive` mechanism (EDR-029). No new language semantics — the macro system already provides code generation at compile time.
- **Classification per D-03:** StdLib. Serialization is a library concern implemented via the existing macro system. The `@derive(Serialize)` annotation invokes a registered macro — no new compiler semantics.

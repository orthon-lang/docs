# Tooling: orthon test — Contract-Derived Tests

> **Status:** Open · **Priority:** P2 · **Target:** M3 (Tooling)
> **Source:** [CONTRACTS](../../what/concepts/CONTRACTS.md) Issue (gap 3: test synthesis); [TRAIT_CONTRACT_UNIFICATION](../concepts/research/essential/TRAIT_CONTRACT_UNIFICATION.md) Step 6 (Tooling Implications)

---

## Description

A CLI tool that derives tests from contracts. For a named contract, or the inline contract of a function, it generates inputs from the parameter types, keeps the inputs that satisfy `requires`, runs every function or type that declares conformance to the contract, and checks `ensures` as the oracle. A failure report names the violated condition by its predicate and the result by its declared name.

## Problem

Contracts are executable specifications, and one contract can have many implementations. Writing the tests that run each implementation against the same contract by hand duplicates the specification, and the copies drift. Without a tool, the benefit "specify once, test every implementation" is lost: contracts are checked only when a function is called in a debug build, and nothing gives systematic evidence that an implementation satisfies its contract.

## Spec Impact

### If this tool exists

- One named contract yields one set of tests for all implementations; a new implementation is tested as soon as it declares conformance.
- When a business rule (a contract) changes, the implementations that no longer fit are found at once (the `withdraw_with_fee` example in the contract-unification hypothesis).
- An implementation generated by an LLM can be checked against the contract before it is used, which supports the specification-first workflow.

### If this tool does NOT exist

- The "test synthesis" motivation of CONTRACTS stays unmet.
- Reuse of one contract across implementations is worth less, because each implementation is tested separately by hand.
- Contract violations are found only on the calls that happen to run.

## Language Feature Dependencies

- **Contracts, the named result, purity** (CONTRACTS, EDR-097) — conditions are pure, so a run is repeatable; `requires` filters inputs; `ensures` is the oracle; the named result and the predicate names appear in reports.
- **Conformance relation** (TRAIT_CONTRACT_UNIFICATION) — the IR must enumerate, for a contract, every function and type that declares conformance to it.
- **Generation of values of a type** — the tool needs a way to produce values of a parameter type. Where this capability is defined (a trait, a compiler service, constrained types) is **open**. Without it, only types with a hand-written generator can be tested.
- **Invariants** (Review decision 18 of the hypothesis) — for mutable types the tool checks the invariant after creation and after each `proc` in a generated sequence of calls.
- **Multi-instance contracts** are deferred to v0.2; when they return, this tool is their natural runner.

## Notes

- Out of scope: proving contracts ([`ORTHON-PROVE.md`](ORTHON-PROVE.md)), generating whole programs.
- Open: reproducibility (seeds), shrinking of failing inputs, time limits, and contracts whose `requires` rejects most randomly generated inputs.
- Whether this is a standalone CLI or part of the compiler's test command is an implementation matter.

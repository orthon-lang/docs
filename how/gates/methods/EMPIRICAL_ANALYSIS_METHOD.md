# Empirical Analysis

> LLM-friendliness cannot be assumed from intuition — it must be
> proven. Skip the grammar inspection and the schema test, and a
> construct that "feels generable" may still hide the exact ambiguity
> or missing schema detail that causes an LLM to hallucinate syntax
> once real generation begins.

---

## Origin

Empirical Analysis combines two established engineering practices,
applied here to language design rather than to running code.
**Structural (static) analysis** inspects a grammar or specification
for known defect patterns without executing anything — the same
discipline used by linters and formal grammar reviewers to catch
ambiguity before it reaches a parser. **Round-trip testing** verifies
that a representation survives serialization and deserialization
without loss of information — the same guarantee schema and protocol
designers demand before trusting a format to carry meaning intact
across a boundary. Applied together, they let a proposal be judged
against evidence rather than against how generable it seems.

---

## Application to Language Design

When evaluating LLM generability, Empirical Analysis formalizes the
two complementary approaches `DECISION_VALIDATION.md` names for the
`LLM_GENERABILITY_GATE`, then scores the result against the gate's
own five-criterion table.

### 1. Run the Structural Scan

Examine the concept's grammar and semantics for known LLM-unfriendly
patterns: ambiguity, special cases, context-dependent syntax, and
tokenizer misalignment. Walk each sub-construct in turn and record
which are clean and which carry risk — a construct with one open,
undecided concrete syntax is exactly the "context-dependent syntax
not yet fixed" pattern this scan is built to catch.

### 2. Attempt the Schema Round-Trip

Express the concept fully in a machine-readable schema (grammar +
type system + stdlib contracts), then ask whether an LLM consuming
only that schema would have enough information to generate correct
code. Distinguish three outcomes per sub-construct: a **full**
round-trip (the schema carries every constraint), a **partial**
round-trip (some constraint is lost or under-specified), or **no**
round-trip (the concept cannot be represented in schema form at all).

### 3. Score Against the Five-Criterion Table

Reproduce the gate's own criteria verbatim — do not invent new
criteria or reorder existing ones:

| Criterion | Pass | Flag | Fail |
|---|---|---|---|
| **Schema-serializable** — the concept is fully expressible in a machine-readable grammar/type schema | Full representation in schema without loss | Partial representation (minor loss of constraints) | Cannot be represented in schema |
| **Predictable generation** — LLM generates the construct correctly in ≥90% of attempts | No known ambiguity or special cases | One identified edge case where LLMs systematically err | Multiple failure modes identified |
| **No hallucination surface** — no ambiguous or confusable constructs | Every form has exactly one meaning | One ambiguous parse possible | Multiple ambiguous or confusable forms |
| **Strategy-aware default** — code generated by default is valid under any Implementation Strategy | Always valid without annotations | Valid under most strategies; requires explicit Policy annotation for some | Generated code systematically violates Strategy constraints |
| **Self-correctable** — Static Analyser can detect and report LLM-generation errors | Full diagnostic coverage (type errors, policy violations, strategy mismatches) | Partial coverage with silent gaps | No or minimal diagnostic support |

### 4. Determine the Verdict

Read the scored table as a whole:

- **All Pass** — the proposal passes the gate outright.
- **Any Flag with no Fail** — per `DECISION_VALIDATION.md`'s Gate
  Flow rule, a Flag "may proceed"; record the flagged criterion's
  root cause so it can be resolved before the proposal's final gate.
- **Any Fail** — the proposal must be revised to address the specific
  fail condition before re-entering the gate.

## Perspective

This method serves the **LLM_GENERABILITY_GATE** — the gate that asks
whether an LLM can reliably produce correct code using a given
construct. It replaces "seems generable" intuition with a concrete
grammar inspection and a schema round-trip test, so hallucination risk
is caught by evidence before a concept is accepted rather than
discovered later during real generation.
